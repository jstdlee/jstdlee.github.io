Komga on Tailscale: Two HTTPS Origins, and a DNAT That Never Arrives

2026-11-10#tailscale#komga#docker#nftables#self-hosted#arm64#internet-archive

TL;DR: Komga on an arm64 box, exposed over the tailnet only. Two things I had wrong: tailscale serve --https is not capped at 443/8443/10000 — Tailscale 1.104.5 accepted --https=25600 and a peer got HTTP 200 on it; and the “tailnet IP ports get dropped” rule applies to Docker-published ports only, because a plain host socket bound to the same tailnet IP answers 200 from the same peer. So the origin port survives and you keep TLS: https://<host>.ts.net and https://<host>.ts.net:25600, both proxying http://127.0.0.1:25600. Everything below was probed, not assumed — and one earlier note of mine was over-generalised, so I narrowed it.

1. The shape of the deploy

services:
  komga:
    environment:
      SERVER_PORT: "25600"
      SERVER_HOST: "0.0.0.0"     # container-internal; the host bind does the isolation
    ports:
      - "127.0.0.1:25600:25600"  # loopback only

No public interface, no reverse proxy of my own. tailscale serve is the TLS layer, because Komga cannot terminate TLS itself. /config stays on local disk — the H2 database corrupts on CIFS/NFS, which is not a theoretical concern here.

2. The probe matrix

First attempt published the port on the tailnet address (-p <tailnet-ip>:25600:25600). It looked right and failed:

ProbeResult
ss -ltnplistening on <tailnet-ip>:25600 only, nothing on 0.0.0.0
curl from the host to its own tailnet IP200
bash /dev/tcp from a peer, port 25600closed
curl from a peerHTTP 000
tailscale ping between the same two nodesanswers fine

ICMP over the tailnet fine, host-local TCP fine, forwarded TCP dropped. That is the signature of Docker DNAT’ing into the bridge network and Tailscale’s nftables FORWARD rules discarding the packet.

3. The counter-probe that narrowed the claim

I had written this up as “Tailscale drops published tailnet ports”. Too broad. Same IP, same port, one difference — no Docker in the path:

$ python3 -m http.server 25600 --bind <tailnet-ip>      # host socket, INPUT path
local: 200
from peer: 200

A socket bound to the tailnet address is served through INPUT. A Docker-published port is DNAT’ed and travels through FORWARD, where Tailscale’s rules live. So the correct rule is: publish nothing on the tailnet IP; let serve do the proxying — serve is itself a host socket, which is exactly why it works.

4. --https is not limited to three ports

$ tailscale serve --bg --https=25600 http://127.0.0.1:25600
https://<host>.ts.net:25600/
|-- proxy http://127.0.0.1:25600

$ ssh peer 'curl -s -o /dev/null -w "%{http_code}" https://<host>.ts.net:25600/health'
200

The documented set (443, 8443, 10000) is what the docs show, not what the daemon accepts. Both origins now serve the same backend, and both return 401 on /api/v1/libraries unauthenticated — which is the proof the request actually reached Komga rather than being answered by the proxy.

5. One origin, or no base URL

SERVER_BASE-URL was pinned to the MagicDNS origin. With a second origin serving the same app, that pin breaks absolute URLs for every other origin. Unset, Komga’s index emits root-relative asset paths and both origins render identically — verified by diffing the href/src set fetched over 443 and 25600:

href="/css/app.c113e1ad.css"   src="/js/app.6fe8f9e4.js"   # identical on both

Rule: pin a base URL only when exactly one origin exists.

6. The library side, where the assumptions were worse

Komga is a media server, not a downloader. Acquisition ran against the Internet Archive, chosen for boring reasons: public domain, stable JSON API, no bot wall.

  • Rate limit is real. 4 s between items kept every request at 200 across 5 items + 5 metadata calls; backoff on 429 is 5 × sleep, 3 tries.
  • Lending-only items answer 401/403. That is a skip, not a failure — the item exists, you may not fetch it. Do not retry, and do not let set -e kill the run on it.
  • jp2.zip is the trap. Komga indexes it happily and renders nothing. The pipeline needs fetch → convert JPEG2000 to PNG → repack as a plain ZIP (Komga rejects RAR5 and solid archives) → move the raw source out of the library, or every item shows up twice.
  • Page order is filename order. Zero-pad (001.jpg), cover first, ComicInfo.xml inside the archive.
  • Soft deletes lie. /api/v1/books totalElements still counts rows whose files vanished; /api/v1/series booksCount does not filter them either. Do not reconcile the two counts.

7. Numbers, with their conditions

Arm64 host, single container, latest image. Healthcheck to healthy in 15 s. Repack of a 291-page JPEG2000 scan to PNG: ~2 min including download — fine as a cron job, not as an interactive loop. Final state: 6 live books, 6 series, 3 fetched, 2 correctly classified as lending-only, 0 failures on the idempotent re-run.

8. Not verified

  • Whether Komga’s continuous scanner ever catches a file without an explicit API scan — the cron recipe assumes it does.
  • The nftables rule itself: reading them needs root, so the FORWARD-drop mechanism is inference from the probe matrix, not a seen rule.
  • Scanlation-tier acquisition: metadata only, no chapter download was run. Public-domain and own-purchase tiers are one thing; derivative-work sources are a legal and malware risk that no amount of tooling changes.
