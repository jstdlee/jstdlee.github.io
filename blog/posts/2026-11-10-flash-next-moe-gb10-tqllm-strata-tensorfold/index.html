Qwen3.8-Flash-Next（125B MoE）在一块 GB10 上的三种落法：tqLLM / Strata / TensorFold，部署与第一份双引擎基准

2026-11-10#qwen3.8#flash-next#tqllm#strata#tensorfold#moe#quantization#gb10#dgx-spark#benchmark

上一篇聊了 prompt cache。这一篇回答另一半问题：GB10（128 GB 统一内存）到底怎么把 125B 的 Qwen3.8-Flash-Next 装进去，装进去之后跑多快。同一个晚上把三个引擎各部署了一轮，其中两个（Strata 的 UD-IQ4_XS、TensorFold 的 NVFP4 checkpoint）完整跑了一套基准：LRU 单发×3 + agent 回放×4（23K 上下文逐轮追加），thinking 开、temperature 0，同一台机器串行跑。tqLLM 这一轮完成的是部署与选型验证（量化文件落在本机的落法），Posts 相关数字见上一篇文章。

三种落法，三种装法

125B MoE 的中心问题只有一句：expert 权重放哪。

tqLLM（TQ 量化）

tqLLM（turbo-tan/tqllm，Docker 镜像 ytan2000/tqllm）是 16–24 GB 消费卡的路线：27B 走 Qwen3.8-27B-TQ3_4S（14.76 GB + DFlash2/DCompute 草稿）；Flash-Next 提供两个方案：TQ3.45 纯量化文件（46.67 GB）与 tqLLM 自家 “mixed” 文件（105.66 GB，8-bit mixer + 内建 N-gram prompt cache）。GB10 上的落点很清楚：46.67 GB 全统一内存没压力，mixed 文件必须牺牲一部分 VRAM 窗口 / KV 才能塞下；长上下文（>64K）时这两方案的差距还不只是内存，是 N-gram prompt cache 的命中率。本轮在 GB10 上完成到部署路径验证（镜像与量化文件落位）；文末列了未验证的部分。

Strata（UD-IQ4_XS + mmap-experts）

Strata 对 Flash-Next 的运行面是 --mmap-experts：experts 走文件 mmap + pack 双层，GPU cache 50.49 GiB（22384 expert 槽），RAM 里 page-locked 4.5→8 GiB resident-copy（budget 55 GiB）。配置文件 strata-flashnext-iq4xs-cached.json（调优过的间隔）：

{"--mmap-experts": "1", "--expert-cache": "22384", "--vram-resident-budget-gib": "55",
 "--prompt-cache": "8", "--prompt-cache-every": "8192", "--prompt-cache-tail": "1",
 "--conversation-cache-mib": "12288", "--conversation-cache-slots": "6"}

启动 2–4 分钟里有一段自检：

strata generate: file set 13.5 GiB does not fit the page cache 0.0 GiB
  -> about 14.5 GB read from the drive per 32768-token prompt (1 chunks);
     no option does better (the set cannot fit: fewest passes win)

这就是 mmap-experts 的物理账：每 32K token 的全新 prompt 都要从 NVMe 翻一次 ~14.5 GB（这块盘 2.5 GB/s）。引擎自己也算了：任何 –resident-budget-gib 加大到 55 GiB 也救不了， 专家区域的免费空间已被 GPU cache 锁死。decode 场景它完全没问题（91.1 % expert 命中 GPU cache）。

TensorFold（NVFP4 checkpoint）

该 repo 的 start.sh 从 HF 直接拉 nvidia/Qwen3.8-Flash-Next-FP4-Local 快照（96 GB，21 shards，qwen4_exp / MXFP8 + NVFP4 + W4A16），218 s 载完：

./start.sh                              # 默认 262144 上下文 · 5 windows · fp8 KV
PARALLEL=2 CONTEXT=131072 PROMPT_CACHE_GIB=8 CACHE_FIRST=1 ./start.sh restart

启动日志最后一次报账：

[tensorfold] CUDA sm_121 device 0 (NVIDIA GB10, memory shared with the host):
  model 75.89 GiB; 2 streams at once, 2.60 GiB each at a 131072-token window
  (fp8 caches), of 20.6 GiB left after a 6.0 GiB reserve; prompts in passes
  of up to 3072 rows, a 8.0 GiB prompt cache; own glue kernels
[tensorfold] serving Qwen3.8-Flash-Next at http://0.0.0.0:8888/v1
  (drafts: on; context: 131072; loaded in 142.5s)

两个引擎的内存窗口互相排斥（TensorFold 的 MemAvailable 闸门 ≈102 GiB，Strata 占着 ~60 GiB 时它直接 refuse），基准必须串行。

基准：两份玩法

同一台机器（GB10 耐性能说明里的 HP ZGX Nano），同一份 harness（一个直打 OpenAI-compatible 端点的 python 脚本 [cmpbench.py] ）：

  1. LRU 单发×3：127 token 代码题（“O(1) get/put LRU cache 实现”，含思考题），temperature 0，max_tokens 8192。第 2、3 发复用第 1 发的 prompt cache，顺手验证短 prompt 的 KV 复用。
  2. Agent 回放×4：一段 ~23K token 的 “ledger archive” 填充文档 + 问题；之后 3 轮各在文末追加一条 follow-up。turn0 是冷 prefill；turnN 命中上一轮缓存，测 TTFT 和 decode tps。

两个引擎的 thinking 都开（TensorFold --thinking 默认 on；Strata server 走 reasoning_content）。全部数字取自服务端日志的自报字段（tok/s、ttft、cached=、MTP 接受率），不用自己算的浮点秒数。

要点：

  • 冷 prefill：TF ~2098 tok/s vs Strata 1180 tok/s（+78 %），根源就是那 14.5 GB NVMe 翻页 vs 全驻 NVFP4。“全驻 GPU” 在 GB10 的 128 GB 统一内存上是成立的。
  • 缓存命中后：TF 的 ttft 常驻 0.26–0.34 s（.cached= 分数 « 23145/23150），Strata turn1/turn2 wall 撑到 9–13 s（多次 follow-up 场景的 prefill 附加 chunk 速率仅 113–148 tok/s，25K 后又高于划过上限）。
  • decode：仍是 TF +25 % 干净利落。Strata 的 MTP 在 deficiency 场景里接受率不掉（suffix drafts: 33 windows, 198 of 293 accepted），草稿质量没问题，收益还得摊到基本盘。

顺带一条（不是我这轮测出来的，但把常驻内存的量级说清楚）：27B 的 DSpine llama-dspine 桌面日常 server（UD-Q4_K_M，262144 ctx，q8_0 KV）稳态吃 ~31 GB；125B MoE 的 KV 空间需求乘了 2.4 倍（MTP 层 + quantized experts 的附加 head），GB10 121 GiB 上限才是真正在玩的约束。

坑（都没少踩）

  1. Strata server 的 pipe 陷阱。起 server 时 bash … | head -40 —— head 输出 40 行后退出，server.py 后面的 stdout 写入直接 SIGPIPE 死掉（第二次请求时 client 端 ConnectionResetError: [Errno 104]，服务端 log 到第一发请求的统计就断）。服务进程必须走文件 redirect 或由 systemd / wrapper 承接。基准第二轮才跑全。
  2. TensorFold ./start.sh 的内存闸门。MemAvailable ≥ ~102 GiB 才放行（缓存加满后剩 97 GiB 直接拒：ERROR: only 97 GiB memory available; a 131072-token window needs ~102 (MEM_CHECK=0 starts anyway)）。装完 Strata 的占用量后起它必须先 stop 那侧；两引擎串行体现在这台机器上。
  3. 两个 HF 库的分量不一样：Qwen3.8-Flash-Next-TQ3_45（46.67 GB），全统一内存可及；自家 mixed（105.66 GB）要吃 system RAM；二者的部署边限不同，混在 “tqLLM 跑 Flash-Next” 一句话里容易踩错。

结论

就 GB10 + Flash-Next 125B 而言，TensorFold 是赢家：decode 43–49 tok/s、冷 prefill ~2100 tok/s、缓存命中 TTFT 0.26–0.34 s。checkpoint 下载要 96 GB、一次性；NVFP4 checkpoint 的质量在本机可对比地得出。

Strata 有自己的场景：decode 场景不好挑效率（都过 GDG），agent 多轮回放比 TF 慢 30–60 % wall time；但 --prompt-cache / --conversation-cache 的组合让 23K→23.4K 的 follow-up 只剩新增 token 的 prefill，跑 ID4_XS 的 pack 生态（其他模型家族）时它仍是那一块 mmap 框架。

tqLLM 的定位是 16–24 GB 卡纯 GGUF 生态（27B TQ3_4S / Flash-Next TQ3.45），digest 的量化文件（46.67 GB）在 128 GB 统一内存播放有富余；但 mixed 文件才是它自家 N-gram prompt cache 的主场——对把 GB10 当 Flash-Next 主力的场景，那条腿没有 TensorFold 好用。

harness一只文件、部署脚本、benchmark 输出统一在 jstdlee/tqllm-fork。

没验证的部分

  • tqLLM 本轮 GB10 上的 tps 没有，两位真实部署完成 27B TQ3_4S 与 Flash-Next TQ3.45 的直接对比留到下一哥 commit；我拿文档、启动日志及（此处）引擎自报数为准。
  • TensorFold 的 W4A16 NVFP4 checkpoint 的量化精度损失没有单独测。“NVFP4 = 官方发布质量” 是 NVIDIA 自报，未在本机做 KL 对照。
