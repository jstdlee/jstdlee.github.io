Ubuntu 24.04 ships FreeRDP with H.264 off. Side-load Debian's libfreerdp3 for AVC444.

2026-11-07#linux#rdp#freerdp#remmina#ubuntu#gnome #issue-12

Remote desktop from dgx to gpd was soft because the client never offered H.264. Ubuntu 24.04 builds libfreerdp3 with WITH_GFX_H264=OFF. GNOME Remote Desktop on gpd already accepts AVC444. The server’s CapsAdvertise line says which one happened, and it flips when the only change is the client’s library path.

gpd is Ubuntu 24.04.5, x86_64, Intel Iris Xe (i915), GNOME on Wayland. gnome-remote-desktop 46.3 serves a headless session on :3389, and intel-media-va-driver 24.1.0 is installed for VA-API encoding. dgx is the client: Ubuntu 24.04, arm64, an NVIDIA GB10, Remmina 1.4.43. The soft picture was a client compile flag. The server was ready.

The Ubuntu build string is the client bug

The arm64 library carries its compile flags as text:

$ strings /lib/aarch64-linux-gnu/libfreerdp3.so.3 | grep WITH_GFX_H264
WITH_GFX_H264=OFF
WITH_OPENH264=OFF
WITH_VIDEO_FFMPEG=OFF

That file is libfreerdp3 3.32.1+dfsg-0ubuntu0.24.04.1. Ubuntu’s packaging builds FreeRDP without FFmpeg, and GFX H.264 is compiled out with it. Debian’s build of the same upstream version keeps FFmpeg, so WITH_GFX_H264 stays on. Ubuntu’s own test patch for this package says so: the test expectations had to change because WITH_GFX_H264 is undefined in the Ubuntu build, and Debian does not need the patch because Debian builds with FFmpeg.

Remmina 1.4.43 reads that string once, in remmina_plugin_entry. gfx_h264_available is true only when freerdp_get_build_config() contains WITH_GFX_H264=ON. It is a build probe. It is not the result of a handshake.

$ remmina --help 2>&1 | grep gfx_h264_available
gfx_h264_available: 0

When the probe is false, the plugin also removes colour depths 65 and 66 from the profile editor. Those two entries are GFX AVC420 and GFX AVC444. A profile file can still contain colordepth=66. In remmina_rdp_main, a false probe rewrites 65 and 66 to 64 before connect. 64 is GFX RFX, and that path clears both FreeRDP_GfxH264 and FreeRDP_GfxAVC444. The profile cannot talk the stock library into advertising H.264.

CapsAdvertise is the negotiation

gnome-remote-desktop logs the GFX capability exchange on every session:

** Message: 18:26:11: [RDP.RDPGFX] CapsAdvertise: Accepting capability set with version RDPGFX_CAPVERSION_107, Client cap flags: H264 (AVC444): false, H264 (AVC420): false

RDPGFX_CAPVERSION_107 is the graphics-channel version. The two booleans are what the client advertised. Both false means no H.264 mode was offered, and the session stays on GFX RFX. RFX is the blurry picture. On this Iris Xe it also skips the VA-API encoder that H.264 uses.

gfx_h264_available: 0 and AVC444: false answer different questions. The first is how the .so was compiled. The second is what this connection offered. The server log is the one that proves the session.

Same FreeRDP 3.32.1, Debian’s flags, a private directory

The fix leaves the Ubuntu package in place. A private directory holds the Debian build of FreeRDP 3.32.1 (WITH_GFX_H264=ON, WITH_VIDEO_FFMPEG=ON) and the FFmpeg 7 libraries that build was linked against. apt upgrade does not overwrite ~/.local.

The directory that was loaded, ~/.local/share/rdp-client/lib/, held 41 shared objects:

libfreerdp3.so.3 -> 3.32.1        WITH_GFX_H264=ON, WITH_VIDEO_FFMPEG=ON
libfreerdp-client3.so.3 -> 3.32.1
libavcodec.so.61                  FFmpeg 7.1.5
libavutil.so.59  libswscale.so.8  libswresample.so.5
+ VA-API, SvtAv1Enc, dav1d, jxl, rav1e, vpx, x265, libdrm, libfuse3, libsso-mib

Two FreeRDP libraries have to override the system copies: libfreerdp3.so.3 and libfreerdp-client3.so.3. They have to be the arm64 objects. gpd is amd64, and it does not need this directory. The bug is on dgx.

libwinpr3.so.3 from that Debian tree is byte-identical to Ubuntu’s (md5 prefix 4176b9f7). It does not have to be carried. ICU resolves to the system libicuuc.so.74 and libicudata.so.74. ldd on the two replaced libraries reports no unresolved symbols.

The FFmpeg 7 objects do have to travel with them. Debian’s libfreerdp3 is linked to libavcodec.so.61. Ubuntu 24.04 ships FFmpeg 6 (libavcodec.so.60), so the system copy cannot satisfy that SONAME. The VA-API and codec libraries in the list are there because libavcodec.so.61 needs them.

~/.local/bin/remmina-h264:

#!/bin/sh
export LD_LIBRARY_PATH="$HOME/.local/share/rdp-client/lib:${LD_LIBRARY_PATH:-}"
exec /usr/bin/remmina "$@"

An earlier draft of this wrapper also pointed OPENSSL_CONF at a file that loaded OpenSSL’s legacy provider next to default. That file can go. A connection with OPENSSL_CONF unset still finishes the TLS handshake and still negotiates AVC444 (18:30:30, H264 (AVC444): true). The server certificate is CN = gpd-rdp.local, O = lan, sha256WithRSAEncryption, 2048-bit RSA. Nothing on that path needs the legacy provider.

The same gpd.remmina profile was connected twice, back to back. The only change was the loader path.

Across the server’s session history, 14 of 15 connections show AVC444: true. The single false is the system-library control run.

colordepth=66 asks for AVC444

In Remmina 1.4.43 the colour-depth values that matter here are:

66   GFX AVC444 (32 bpp)
65   GFX AVC420 (32 bpp)
64   GFX RFX (32 bpp)

66 turns on FreeRDP_GfxH264 and FreeRDP_GfxAVC444, then stores a colour depth of 32. 65 turns H.264 on and forces AVC444 off, which is the AVC420 session. AVC444 keeps 4:4:4 chroma. That is the difference between crisp text and the softer 4:2:0 of AVC420. On this profile, a depth other than 66 comes back as AVC420.

The stock library never reaches that branch for 66. The false probe has already rewritten it to 64.

The other repairs give up the server that already worked

Rebuilding Ubuntu’s FreeRDP works, and the result is a system package. The next apt upgrade replaces it. The rebuild also wants an arm64 toolchain and an FFmpeg new enough for that tree. The private directory sits outside apt.

apt install freerdp3-x11 installs this same Ubuntu build, the one with the codec off. No Ubuntu PPA publishes a WITH_GFX_H264=ON build for this arm64 client.

RustDesk or NoMachine would avoid the codec by leaving RDP. gnome-remote-desktop is already the server on gpd, already authenticated, already listening on :3389. It is the path that can do H.264 and AVC444 on this Iris Xe. Replacing the protocol throws that away to get around a compile flag.

Staying on RFX is the stock fallback. It is the soft session this note started from.

What is actually listening on gpd

The process that owns :3389 is gnome-remote-desktop-daemon --headless (pid 2615254 when this was taken), beside a separate --system instance. gnome-remote-desktop.service is inactive (dead). The user unit is not serving the session. The headless daemon was started next to it.

After apt moves FreeRDP, run the probe again

The private directory will not be overwritten. It can still break if libwinpr3 is left to the system copy and that copy stops matching. Today the two copies of libwinpr3.so.3 are the same bytes, both from FreeRDP 3.32.1. After apt upgrade moves libwinpr3 or libfreerdp3 to a newer upstream, open Remmina through the wrapper and read two lines: gfx_h264_available on the client, and CapsAdvertise on gpd. If ldd on the side-loaded libfreerdp3.so.3 starts reporting missing symbols, put the matching Debian libwinpr3.so.3 back into the private directory.
