Prompt Cache in tqLLM, and What Three Other Engines Learned About It

2026-11-10#prompt-cache#tqllm#dspine#strata#tensorfold#llm-inference#kv-cache#llama.cpp#gb10

TL;DR — --prompt-cache on in tqLLM 1.4.1: each request slot keeps its conversation, a new request is routed to the slot that already holds the largest part of its prompt, and only the new part is prefilled. Eight concurrent agent sessions on a GB10: 11.9 vs 4.5 tok/s total, first token 7 s vs 30 s. The flag is off by default, and the build says out loud why: a reused prompt is not byte-identical to an uncached one, so under --exact on the server prints a warning. Everything below is what three other engines — DSpine, Strata, TensorFold — found about the same flag under different names, and they all hit the same four walls.

1. tqLLM: from one slot to routing by overlap

The single-slot version was in the options table first: --prompt-cache on|off, default off, “keep the previous turn’s KV so a follow-up does not re-read the document” — one slot, on with --kv-compact. Useful for one long document read repeatedly by one client.

1.4.1 makes it a routing decision. With --np > 1, every slot keeps its own conversation, and the server sends an incoming request to the slot that already holds most of its prompt. That is the whole trick: the cache stops being a per-connection buffer and becomes a placement policy. The payoff is not throughput on a hot prompt — it is the first token, which is what an agent actually feels: 7 s instead of 30 s.

The honesty clause matters more than the speed. A cached path and a cold path are different code paths; if they produced identical bits, nobody would need the warning. tqLLM keeps --exact on as the reference mode (FP16/BF16 activations and KV, no int8/FP8 GEMMs, no CPU-served experts) and treats the cache as an explicit approximation inside it.

Same GB10, same client, same prompts, prefill — against TensorFold 1.2.2 (tqLLM on its mixed Flash-Next file with 8-bit mixers, TensorFold on its MLX 4-bit folder):

PrompttqLLMTensorFold
8K4.32 s4.90 s
16K8.14 s9.21 s

64K35.64 s38.11 s

1.07–1.13×. Which is the point: the last 10 % of prefill is not where the story is. The story is whether the cache is on at all, what it can name, and what it refuses.

2. DSpine: the cache that quietly wasn’t there

DSpine runs on the dspine branch of llama.cpp. Qwen3.8-27B is hybrid: 64 layers, 16 of them full attention, the rest recurrent. So the prompt cache is not just KV — the recurrent layers need their memory state snapshotted at checkpoints, and target + drafter together need about 11.2 GiB of prompt state at 262k context.

The default cap is --cache-ram 8192 MiB. Over the cap the server does not shrink the cache. It skips it:

W srv alloc:  - prompt state size 11201.045 MiB exceeds cache size limit 8192.000 MiB, skipping

Decode looked fine (~33 tok/s). Every turn just re-prefilled from token zero, which is 40–80 s of silence before the first token. --cache-ram 24576 fixed it: same 25k prompt, second request cached 25060 / 25064 tokens, 3.59 s end to end against ~150 s cold.

Two related knobs worth knowing: --cache-idle-slots keeps idle slots’ prompt cache alive for the next task (and clears it under unified KV), and POST /slots/{id}?action=save|restore|erase makes the cache an inspectable object instead of an accident of process lifetime. A cap nobody measured is a silent off switch — the only reason I found this one was the log line.

3. Strata: the cache as a number you can argue with

Strata exposes the cache as first-class metrics:

vllm:prefix_cache_queries_total   Prompt tokens looked up in the prompt cache.
vllm:prefix_cache_hits_total      Prompt tokens the prompt cache already held.

Three things I’d copy:

  • prompt_cache_key groups requests; it never decides identity. The responses layer says so explicitly — a client-supplied string cannot make the engine reuse something it shouldn’t.
  • --prompt-cache-tail is a benchmark-only dimension. It is measured in the tuning sweep and dropped at export, because the production interface doesn’t accept it: a winner that depended on it wouldn’t survive. The report says so.
  • verify_exported() re-measures the configuration as it will actually be exported, and if the retest doesn’t reproduce the result, the recommendation is withdrawn. That single function is what separates a tuning matrix from a wish list.

And the bench hygiene that makes any of it meaningful: every prompt is prefixed with a unique per-run tag so no measured run can be served from another run’s prefix cache. My own first benchmark did exactly that — every prompt shared the chat-template prefix, so cached == 0 could never hold and the run measured the cache it was trying to prove.

4. TensorFold: cap, eviction, and what a cache can name

TensorFold’s changelog reads like a list of the ways a cache lies to you.

The cache is what’s left over. Every stream takes a full window at start-up; five windows are 23.9 GiB, and the prompt cache is the pool remainder — 3.4 to 5.1 GiB. --prompt-cache-gib is a cap, not a reservation: on CUDA it can only lower that remainder, never raise it, and it binds only when the leftover is bigger. --prompt-cache-over-cap is refused on CUDA (it lifts a Mac’s 70 % cap). A bigger cache for long multi-turn prompts costs streams or context — that trade is the whole setting.

It has a regression test for the hit. tools/prompt_reuse.py 30000 checks that a follow-up resumes. When a patch starved the cache to 0.2 GiB, that test failed immediately: a 32k-token follow-up resumed 4.7 % of its prompt and prefilled again, 13.8 s. Most projects would have shipped that as a memory win.

Identity is not token equality. Concurrent _slot_for reuses only a strictly shorter matching cached prompt — so an identical prompt is not automatically a prefix-cache hit, and repeated-identical and genuinely-extended conversations must be measured separately. Image prompts were worse: placeholder rows are all the same token, so a token match cannot name the prompt at all, and every turn of a conversation with a screenshot re-prefilled the system prompt. Patch 0030 gives the media its own identity (length-prefixed fields, up to 248 bits, no key under 4 rows).

Concurrency has teeth. A second concurrent fill returned PromptBuffersBusy; a resume’s MTP absorb could overwrite another prompt’s open chunk. Patch 0021 fills one at a time; patch 0029 is free-after-drain plus admission reclaim. Eviction during a read is the classic use-after-read.

Even the graph cache has to name things correctly. PARALLEL=1 builds a graph-capable engine whose cache keys include row count, context bucket and recurrent-state parity; the multi-stream path closes over per-slot state and cache pointers, so a cache keyed only by total row count is insufficient — it needs slot identity, row span, context bucket, recurrent parity, vision rotary mode.

And the accounting is honest about itself. prefill_seconds_total measures time to first callback, which can include scheduler waiting; prefill_s can include building the initial draft chain. Neither should be quoted unqualified as GPU prefill time. A warm-prefix run (median cached 90 of 91 tokens) is labelled as warm, not compared as if uncached.

5. Four engines, four walls

WallWhere it shows
IdentityTensorFold: image rows are one token; only a strictly shorter match counts. Strata: prompt_cache_key groups, never identifies. tqLLM: routing by overlap is an identity decision.
CapacityDSpine: an 8 GiB default silently skips an 11.2 GiB state cache. TensorFold: cap ≠ reservation; the cache is pool leftover.
ConcurrencyTensorFold: PromptBuffersBusy, absorb overwriting another prompt’s chunk, free-after-drain. tqLLM: one slot per conversation, routed.
ProofStrata: per-run tags, benchmark-only levers, verify_exported. TensorFold: prompt_reuse.py, and a benchmark guard that finally distinguishes a hit from a miss.

The engines that hold up do the same four things: the hit is counted, the cap is named and measured on the machine it runs on, identity is kept separate from content, and non-equivalence between the cached and cold path is warned about at runtime — which is exactly what --prompt-cache on does in tqLLM, and why I leave it on with the warning rather than pretend the two paths are the same.
