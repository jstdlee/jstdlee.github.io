DSpine 推理首 token 很慢：混合架构 prompt 状态缓存超过 8 GiB 被跳过——用 --cache-ram 修掉

2026-11-09#llama.cpp#dspine#gb10#dgx-spark#qwen3.8#speculative-decoding#prompt-cache#ollama#troubleshooting #issue-13

DSpine 是给 tencent/Qwen3.8-27B 做投机解码的草稿模型（aj9o9/Qwen3.8-27B-DSpine-b16-GGUF，五层 drafter 读目标模型 5 个层 [2,17,32,47,62] 的隐状态，串行 last-write 精修出 16×16 转移表）。这张卡是 HP ZGX Nano（NVIDIA GB10，128 GB 统一内存），Qwen3.8 是 27B 的 qwen35 混合架构：64 层里只有 16 层全注意，其余是 recurrent（SSM）层。

我把 fork（Ajay9o9/llama.cpp dspine 分支，pinned d493f841）在 Docker 里编译后起了 llama-server，-c 262144，q8_0 KV，-fa on，--reasoning-budget 0，经 magpie 给本机 agent 当 provider。现象是：decode 有 ~33 tok/s（n-max=7 实测最好，比 3090 推荐的 15 快），但 agent 每回合都感觉慢——慢的不是生成，是每一回合都要等 40 秒以上的 prefill。

抓到的那一行

把 /v1/chat/completions 用同一段 25k token 的 prompt 打两次，两次都完整 prefill，第二次反而更慢（47 s → 60 s）。翻 llama-server 日志：

W srv alloc:  - prompt state size 11201.045 MiB exceeds cache size limit 8192.000 MiB, skipping

混合架构的 prompt 缓存不是纯 KV：recurrent 层要把记忆状态按 checkpoint 存快照，目标 + drafter 两个模型的 state + checkpoints 合计约 11.2 GiB。server 的 prompt cache 默认上限是 --cache-ram 8192 MiB，超了就跳过整条缓存——于是每一回合从零 prefill，每秒 600–750 tok/s 的预填速度乘上 25k–50k 的 agent prompt，就是 40–80 秒的沉默。

修复

run 参数加一行：

--cache-ram 24576   # 装下一份 262k 上下文的 state 快照（约 11.2 GiB）+ 余量

重启后验证：同一 prompt 第二次请求 cached 25060 / 25064 tokens，端到端 3.59 秒（冷启动 ~150 s）。agent 回合真正要 prefill 的只剩新追加的内容，速度上限回到 prompt 增量 + 生成速度本身。

顺带的两个实测结论：

  • --spec-draft-n-max 在 GB10 上扫 {2,4,7,15}（512 token 代码题，tok/s 25.1 / 30.5 / 33.6 / 30.8）：7 最优，RTX 3090 文档推荐的 15 在这张卡上反而亏（verify batch 太重）。
  • -lv 4 能在启动日志确认走的就是 DSpine 而不是 DFlash2/MTP 分支：DSpine code bridge (code = 1024, rank = 512, top-k = 16)，且目标模型的 blk.64.nextn.*（MTP 层）被明确 ignore。

对 Ollama

Ollama 内置的是原生 llama.cpp，DSpine 走的是 fork 的 dflash 架构扩展，官方版拒绝加载这类 GGUF（模型卡也写明 stock llama.cpp 直接拒绝而不是跑错）——DSpine 目前只能在 fork 或上游合入后使用。等上游/Ollama 跟进 DSpine 时，这两条迁移到 Ollama 侧同样成立：

  1. 同样的 prompt state size … exceeds cache size limit … skipping 会出现在 Ollama 的 server log 里，它没有暴露 --cache-ram 这类开关——在混合架构、大上下文场景下要么等它自动调大，要么把 -c 压回去。
  2. n-max 别抄 RTX 3090 的 15：带宽越紧张（GB10 这类）verify batch 越贵，实测 7 比 15 快且显存友好（27B Q4_K_M + 草稿 + q8_0 KV @256k 全在统一内存也才 ~25 GiB）。

硬化配置（顺手记录）
